# 기술 문서 작성

프로젝트의 기존 문체와 사용자의 언어를 따르고, 증거와 결론을 구분해 작성합니다.

## 보안·리버스 엔지니어링 문서 출력

리버스 엔지니어링/침투 테스트/CTF/보안 분석이 완료되고 사용자가 문서 생성을 요청하면 **사용자 프로젝트 디렉터리**에 정식 기술 문서를 생성합니다.

### 생성 조건

1. 사용자가 보고서나 문서 작성을 명시적으로 요청했습니다.
2. 보고서에 담을 분석 결과와 근거가 준비되었습니다.

### 템플릿 선택

| 작업 유형 | 사용할 템플릿 |
|---------|---------|
| APK/바이너리 리버스 엔지니어링 | `references/security-report-templates.md` → 리버스 엔지니어링 보고서 |
| 침투 테스트/취약점 분석 | `references/security-report-templates.md` → 침투 테스트 보고서 |
| CTF 문제 해결 | `references/security-report-templates.md` → CTF 풀이 |
| JS/Web 시그니처 분석 | `references/security-report-templates.md` → 시그니처 분석 보고서 |
| 일반 기술 문서 | `references/templates.md` → README / API 문서 |

### 출력 사양

- **출력 위치**: 사용자의 현재 프로젝트 디렉터리(스킬 패키지 디렉터리 아님)
- **파일 이름 형식**: `YYYY-MM-DD_[유형]-[대상약칭]-report.md`
- **프로젝트에 `docs/` 디렉터리가 있는 경우**: `docs/` 아래에 우선 배치합니다.
- **인코딩**: UTF-8
- **언어**: 사용자의 대화 언어와 프로젝트의 기존 문체를 따릅니다.

### 품질 요구 사항

- 모든 코드 블록은 검증된 예시이거나 의사 코드/승인된 실습 환경 전용임을 명확히 표시해야 합니다.
- 최종 산출물에는 미해결 placeholder/TODO가 없습니다.
- 주요 결과는 증거로 뒷받침되어야 합니다.
- 재현 단계는 승인된 범위에서 제3자가 독립적으로 재현할 수 있어야 합니다.
- 민감한 정보(실제 토큰, 비밀번호, 내부 URL)는 자리 표시자로 대체됩니다.

### 차트 통합

관계나 흐름이 글보다 명확해지는 경우에만 프로젝트의 `diagram-generator` 모듈을 참고해 차트를 포함합니다.

| 보고서 유형 | 추천 차트 | 차트 종류 |
|---------|---------|---------|
| 리버스 엔지니어링 보고서| 함수 호출 다이어그램, 데이터 흐름 다이어그램| Mermaid 순서도/시퀀스 다이어그램|
| 침투 테스트 보고서| 공격 경로 맵, 네트워크 토폴로지 맵| Mermaid 흐름도/그래프비즈|
| CTF Writeup | 문제 해결 아이디어 흐름도| Mermaid flowchart |
| JS 시그니처 분석 보고서 | 요청 흐름 시퀀스 다이어그램, 알고리즘 흐름도 | Mermaid 시퀀스 다이어그램/흐름도 |

차트는 보고서 마크다운에 Mermaid 코드 블록으로 포함되어 GitHub/GitLab에서 직접 렌더링이 가능합니다.

## 핵심 원칙

### 1. 점진적 공개

정보를 다음 순서로 배치합니다.

| 계층 | 내용 | 독자의 질문 |
|-------|---------|---------------|
| 1 | 한 문장 설명 | 무엇인가요? |
| 2 | 빠른 시작 코드 블록 | 어떻게 사용하나요? |
| 3 | 전체 API 참조 | 어떤 옵션이 있나요? |
| 4 | 아키텍처 심층 분석 | 어떻게 작동하나요? |

**경고, 주요 변경 사항 및 전제 조건은 맨 위에 표시됩니다.**

### 2. 작업 중심 작성

```markdown
<!-- Bad: Feature-oriented -->
## AuthService Class
The AuthService class provides authentication methods...

<!-- Good: Task-oriented -->
## Authenticating Users
To authenticate a user, call login() with credentials:
```

### 3. 구체적인 예시 제공

모든 개념에는 구체적인 예가 필요합니다.

## 형식 기준

- **일관된 제목 스타일**: 같은 문서에서 명사형·문장형 제목을 혼용하지 않습니다.
- **최대 3개 제목 수준**: 깊이가 깊어질수록 문서가 분할됨을 의미합니다.
- 코드 블록에 **항상 언어 지정**
- 내부 링크의 **상대 경로**
- 3개 이상의 속성이 있는 구조화된 데이터용 **테이블**

## 품질 체크리스트

- [ ] 테스트되고 실행 가능한 코드 예제
- [ ] 자리 표시자 텍스트 또는 TODO 없음
- [ ] 실제 코드 동작과 일치
- [ ] 모든 내용을 읽지 않고도 스캔 가능
- [ ] 독자는 다음에 무엇을 해야 할지 알고 있습니다.

## 피해야 할 패턴

| 문제 | 개선 방법 |
|---------|-----|
| 텍스트의 벽 | 제목, 글머리 기호, 코드, 표로 구분|
| 묻혀 있는 중요 정보 | 경고, 주요 변경 사항, 전제 조건을 문서 앞부분에 배치 |
| 누락된 오류 문서 | 발생 가능한 오류와 대응 방법을 문서화 |

## 라우팅 컨텍스트

**업스트림 입력**: 보안/리버스 엔지니어링 결과를 사용자가 문서화해 달라고 요청할 때 이 모듈을 사용합니다.
**트리거 방법**:
- 수동: 사용자가 "보고서 작성", "문서 출력", "작성"이라고 말합니다.

**동일 레벨 관련 모듈**:
- `apk-reverse/` — APK 리버스 엔지니어링이 완료된 후 리버스 엔지니어링 보고서를 생성합니다.
- `ida-reverse/` — 바이너리 분석이 완료된 후 리버스 엔지니어링 보고서 생성
- `radare2/` — CLI 분석 완료 후 리버스 엔지니어링 보고서 생성
- `js-reverse/` — JS 서명 리버스 엔지니어링이 완료된 후 서명 보고서 생성
- `reverse-engineering/` — 일반 리버스 엔지니어링이 완료된 후 리버스 엔지니어링 보고서를 생성합니다.
