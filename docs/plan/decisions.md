# 미결 결정사항 (Decision Register)

기획 단계에서 **결정하지 않고**, 각 갈림길의 옵션·장단점·근거를 기록한다. **결정은 구현 단계에서.**

- 표기: 각 항목에 *비구속 메모*(현재 기우는 방향, 강제 아님)와 *결정 시점*을 단다.
- 전제(이미 확정 — 옵션 아님): 안전 불변식 = **대상 불간섭**(설치/실행/빌드/계측 금지), 읽기전용, 사람 최종판정, 도구설치·메타조회 ≠ escalation.
- 상세 근거: `../research/capability-tiers.md`, `../research/reverse-skill-harvest.md`, `../research/threat-catalog.md`.

---

## D1. 엔진 substrate (구현 언어/런타임)

| 옵션 | 장점 | 단점 |
|------|------|------|
| **bash** | macOS 기본만으로 제로 의존·이식성 최고 | 구조 파싱·신뢰도 점수·다단계 추적 구현 빈약, regex 한계 |
| **python3** | 매니페스트/AST 파싱, LIEF·capa·semgrep 등 라이브러리 직접 연동, 점수 모델 자연스러움 | python3 런타임 가정(대다수 dev 머신 존재하나 "요구"는 함) |
| **go / rust** | 단일 바이너리 배포·성능 | 개발/이식 부담, 빌드 필요, 라이브러리 생태계 약함 |

- *비구속 메모*: Tier-0 코어를 **python3 가정**이 균형적(파싱·라이브러리·점수 모델). 순수 bash는 "정말 어디서든"이 필요할 때. → D1은 D2(Tier 범위)와 연동.
- *"제로 의존"의 정의*: **운영자가 스캐너를 위해 별도 도구를 설치할 필요 없음**을 뜻한다(무네트워크·번들 데이터 포함). ⚠️ 최신 macOS(14+)는 python3를 기본 탑재하지 않으며 CLT/개발환경에서 흔히 존재할 뿐이므로, "macOS 기본 = python3 보장"으로 읽지 말 것. 따라서 substrate 선택과 무관하게 **파서 부재 시 동작**을 반드시 정의한다(아래).
- *안전 조건(구속)*: 구조 파서(python3/node/jq)가 없어 매니페스트를 정밀 파싱하지 못하면, grep fallback의 under-parse를 **완화 신호가 아니라 상승 신호("정밀 검사 불가")로 보고하고 fail-closed**한다. 파서 부재가 조용한 녹색 판정으로 이어지면 S3(사람 최종판정)·미탐 방지 원칙에 위배된다. (2026-07-05 보안 리뷰 반영)
- *결정 시점*: 구현 착수 시(M1). 단 위 *안전 조건*은 옵션이 아니라 어느 substrate에서도 지켜야 하는 요건.

## D2. Tier 구현 범위 + 도구 채택

| 옵션 | 장점 | 단점 |
|------|------|------|
| **Tier-0만** | 자체완결·즉시 실행·유출 0 | 탐지 상한(휴리스틱/regex), 알려진 악성·취약은 번들 DB 한정 |
| **Tier-0 + 선택적 Tier-1** | 무설치 기본 + 도구 있으면 심화. 점진 확장 | 도구별 어댑터·버전·출력 정규화 복잡도 |
| **풀 오케스트레이션(도구 필수)** | 탐지 품질 최고(GuardDog/Semgrep/OSV 등) | 운영자 설치 부담, 이식성·즉시성 저하 |

- *비구속 메모*: **Tier-0 코어 우선(M1–4) → Tier-1 어댑터 점진(M5)**. Tier-1 1차 후보는 미션 직결 Top 5(GuardDog·Semgrep·OSV-Scanner·YARA-X·gitleaks). 어떤 도구를 1차에 넣을지는 구현 시.
- *결정 시점*: M5 착수 시(도구별로 개별).

## D3. 규칙 저장 방식

| 옵션 | 장점 | 단점 |
|------|------|------|
| **코드 내장 데이터표** | 자체완결·단일 배포·룰 자체 신뢰(외부 파일 변조면 없음) | 룰 추가에 코드 수정, 비개발자 기여 어려움 |
| **외부 규칙 파일(YAML/JSON)** | 확장성·커뮤니티 룰(Semgrep/YARA) 활용 | 추가 파일 의존, **외부 룰 자체의 신뢰 검증** 필요 |
| **혼합** | 내장 코어 + 외부 룰 옵트인 | 두 경로 유지 |

- **결정: 채택 기준선 = 코드 내장 데이터표** (2026-07-05). proposal §4.2가 규칙을 "엔진 내부에 내장 — 외부 파일 의존 없음"으로 설계하므로, 코어 규칙은 내장 데이터표로 확정한다. 외부 규칙 파일(Semgrep `p/trailofbits`, YARA-X 룰셋)은 **Tier-1 옵트인**으로만 추가하며 "운영자가 의도해 도입한 도구"로 취급한다(혼합 방식). 남은 세부(내장 표의 스키마·필드)는 M1 설계 시 확정.
- *결정 시점*: 기준선은 확정(위). 스키마 세부는 M1(코어 규칙 모델 설계 시).

## D4. 네트워크 기본 정책 + 데이터 갱신

| 옵션 | 장점 | 단점 |
|------|------|------|
| **기본 오프라인** | 유출 0·프라이버시·결정론적 | 평판·최신 `MAL-` 보강 못 받음(번들 DB stale) |
| **기본 온라인 + `--offline`** | deps.dev 평판·배포일·다운로드수 등 풍부 | 대상 의존성 이름·버전이 제3자에 노출(프라이버시 고지 필요) |

- **결정: 기준선 = 기본 오프라인(0 egress)** (2026-07-05, proposal §2.3와 정합). 세부:
  - 취약/악성 탐지는 **번들 OSV DB로 오프라인 1차**(Tier-0, 유출 0) — 기본 동작.
  - deps.dev/레지스트리 **평판 보강은 온라인·Tier-1, `--online` 옵트인**(기본 OFF) + 프라이버시 고지("대상 의존성 이름·버전을 제3자에 전송").
  - **현행 MVP `scan.sh`는 네트워크 일절 없음** — 온라인 계층은 M5에서 도입.
  - > 이 결정이 D4의 단일 근거다. proposal·`../research/capability-tiers.md`·`../research/reverse-skill-harvest.md`의 네트워크 서술은 모두 이 정책으로 정규화한다(구 "기본 ON"·"OSV=escalation" 표기는 폐기).
- *남은 결정*: 번들 DB 갱신 주기(수동 vs 주기적) → M5.
- *결정 시점*: 기준선은 확정(위). 온라인 계층 세부는 M5(의존성 인텔 통합 시).

### D4a. release-age / cooldown 정책

| 도구 | 정책 후보 | 메모 |
|------|-----------|------|
| npm | `min-release-age`, `min-release-age-exclude` | 최근 배포 버전 설치를 지연. 내부 패키지는 exclude 필요 가능 |
| pnpm | `minimumReleaseAge`, `minimumReleaseAgeExclude` | v11 기본값 1440분. 명시 설정 시 strict 동작 검토 |
| Bun | `minimumReleaseAge`, `minimumReleaseAgeExcludes` | 초 단위 설정. root lifecycle script 실행과 별도로 봐야 함 |
| Yarn modern | `npmMinimalAgeGate`, `npmPreapprovedPackages` | `.yarnrc.yml` 정책으로 관리 |

- *비구속 메모*: 낯선 대상 기본 설치 정책 후보로 1일 이상 cooldown을 검토하되, lockfile 재현성/내부 패키지 예외와 충돌할 수 있어 구현 단계에서 결정한다.
- *결정 시점*: 설치/실행 게이트 정책 확정 시.

## D5. 출력 형식

| 옵션 | 장점 | 단점 |
|------|------|------|
| **md만** | 사람 친화, 무설치 | 기계 처리·CI 게이트 약함 |
| **md + json** | CI 게이트·후처리·집계 | 스키마 설계·유지 |
| **+ SARIF** | 표준(GitHub code scanning/IDE 연동) | 오버헤드, 매핑 작업 |

- *비구속 메모*: **md 기본 + `--json` 옵션**. SARIF는 수요 생기면 차후.
- *결정 시점*: M4(출력 자동화 시).

## D6. 시각화

| 옵션 | 장점 | 단점 |
|------|------|------|
| **텍스트 화살표 체인** | 완전 무설치, 어디서나 | 단순·정적 |
| **Mermaid 소스 인라인** | GitHub/GitLab 무설치 렌더, 편집가능 | 그 밖에선 소스만 보임 |
| **렌더 이미지(PNG/SVG)** | 독립 이미지 | 렌더 도구 설치 필요(mmdc/Graphviz) → optional/escalation |

- *비구속 메모*: **텍스트 1순위 + Mermaid 소스 옵션**(다단계 트리거 흐름). 이미지 렌더는 옵션.
- *결정 시점*: 보고서 설계 시(M4 전후).

## D7. 심각도 등급 체계

| 옵션 | 장점 | 단점 |
|------|------|------|
| **3단계(HIGH/MED/INFO)** | 단순·기존 호환 | reverse-skill 4단계(고/중/저/정보)와 매핑 필요 |
| **점수 + 구간 매핑** | 신뢰도(severity×confidence) 표현, 가중 | 구간 임계 튜닝 필요 |

- **결정: 채택 기준선 = 3단계(HIGH/MED/INFO) + confidence 점수 병기** (2026-07-05). proposal §4.5가 `최종등급 = bucket(severity×confidence)`로 설계하므로 3단계 유지 + 점수 병기를 확정. 외부 도구 등급·reverse-skill 4단계는 3단계로 정규화. 남은 세부(구간 임계값 튜닝)는 M2에서.
- *결정 시점*: 기준선은 확정(위). 임계값 튜닝은 M2(점수 모델 설계 시).

## D8. escalation 핸드오프 방식

| 옵션 | 장점 | 단점 |
|------|------|------|
| **보고서 포인터만** | 단순·결합도 낮음 | 수동 |
| **reverse-skill 심층티어 자동 라우팅** | 발견 카테고리 → 심층모듈 연결 | 결합·심층티어 의존 |

- *비구속 메모*: **보고서에 "이 발견은 X 심층 모듈로" 포인터**(routing.md 패턴). 자동 실행은 안 함(승인 게이트 유지).
- *결정 시점*: 보고서/플로우 확정 시.
