# OSV 데이터 쉽게 이해하기

## 한 문장 설명

OSV는 **오픈소스 패키지의 알려진 보안 문제를 컴퓨터가 읽을 수 있게 정리한 공개 신고서 모음**이다.

백신에 비유하면 다음과 같다.

- 프로젝트의 lockfile·manifest: 현재 사용 중인 부품 목록
- OSV 데이터: 문제가 신고된 부품과 버전 목록
- OSV-Scanner: 두 목록을 대조하는 프로그램

OSV 데이터와 OSV-Scanner는 같은 것이 아니다. 데이터는 목록이고, Scanner는 목록을 읽어 비교하는 도구다.

## 무엇이 들어 있는가

OSV.dev는 GitHub Advisory Database, Go Vulnerability Database, RustSec, PyPI Advisory Database, OpenSSF Malicious Packages 등 여러 출처의 레코드를 모은다. 각 레코드는 보통 다음 정보를 가진다.

- 어떤 생태계와 패키지인지: npm, PyPI, Go, Maven, NuGet 등
- 어떤 버전이 영향을 받는지
- 문제의 설명과, 제공되는 경우 심각도
- 수정된 버전이나 관련 링크
- 레코드가 언제 수정됐는지

공식 설명과 데이터 출처는 [OSV 소개](https://google.github.io/osv.dev/)와 [OSV 데이터 출처](https://google.github.io/osv.dev/data/)에서 확인할 수 있다.

## 취약한 패키지와 악성 패키지의 차이

둘은 다르다.

**취약한 패키지**는 원래 정상적인 패키지지만 버그 때문에 공격당할 수 있는 패키지다. 예를 들어 특정 버전의 이미지 라이브러리에 파일을 열 때 코드가 실행되는 취약점이 있을 수 있다.

**악성 패키지**는 특정 패키지나 버전에 정보 탈취, 백도어 설치, 파괴 같은 의도적 악성 행위가 포함된 경우다. 처음부터 악성일 수도 있고, 정상 패키지의 계정·배포 경로가 탈취되거나 변조돼 악성 버전이 생길 수도 있다. OpenSSF는 이런 신고를 OSV 형식으로 공개하며, 흔히 ID가 `MAL-...` 형태다. 자세한 범위는 [OpenSSF Malicious Packages](https://github.com/ossf/malicious-packages)에 정리돼 있다.

Secure Onboard가 npm 설치 작업을 판정할 때는 `MAL-` 악성 패키지 정보가 특히 직접적이다. 일반 취약점 정보도 유용하지만, 취약점 하나가 있다는 이유만으로 현재 설치 작업을 HIGH로 차단할 수 있는 것은 아니다.

## 실제 검사에서는 어떻게 쓰는가

1. 대상의 lockfile·manifest에서 패키지 이름과 버전을 **정적으로 읽는다**.
2. 로컬에 저장된 OSV 레코드에서 같은 패키지와 버전을 찾는다.
3. 알려진 악성 패키지 또는 취약 버전과 일치하면 증거로 기록한다.
4. 다른 정적 분석 결과와 함께 해당 작업의 `HIGH`, `LOW`, `INFO` 판정에 반영한다.

OSV-Scanner도 패키지 정보 추출과 취약점 대조의 두 단계로 동작한다. 이미 내려받은 로컬 DB를 쓰는 `--offline` 모드도 제공하며, 이 모드는 DB를 갱신하거나 프로젝트·의존성 정보를 전송하지 않는다. `--offline-vulnerabilities`만 사용하면 다른 기능은 네트워크를 쓸 수 있으므로 이 프로젝트의 완전 오프라인 대조와 같지 않다. 자세한 내용은 [OSV-Scanner 오프라인 모드](https://google.github.io/osv-scanner/usage/offline-mode/)에서 확인할 수 있다.

## OSV가 해주지 못하는 것

OSV만으로 프로젝트나 설치 작업의 안전을 보증할 수는 없다.

- 아직 신고되지 않은 새 악성 패키지나 제로데이는 모른다.
- 프로젝트 안에 직접 들어 있는 악성 코드를 찾지 않는다.
- 취약한 함수가 실제 실행 경로에서 사용되는지 항상 판단하지 않는다.
- 데이터가 오래되면 최근 신고를 놓친다.
- 잘못 신고되거나 철회된 레코드가 있을 수 있다.
- OpenSSF 악성 패키지 저장소에는 경계 사례가 포함될 수 있고 부분 버전 오탐 처리는 아직 완전하지 않다.

따라서 OSV는 여러 검사 근거 중 하나이며, 자체 정적 분석과 함께 사용해야 한다.

## 왜 “전체 DB를 넣을지”가 문제가 되는가

OSV는 모든 생태계를 합친 전체 다운로드와 npm·PyPI 같은 생태계별 다운로드를 제공한다. 변경된 항목만 받기 위한 목록도 제공한다. 전체 DB에는 이 프로젝트가 당장 지원하지 않는 운영체제·언어·생태계의 레코드까지 들어가므로 패키지 크기, 갱신 시간, 저장 공간, 라이선스·무결성 관리 부담이 커진다.

선택지는 다음과 같다.

1. **악성 패키지 목록만 포함**
   - 가장 작고 제품 목적에 직접적이다.
   - 일반적인 CVE·GHSA 취약점은 놓친다.
2. **지원 생태계별 데이터팩 포함**
   - npm·PyPI·NuGet·Maven처럼 실제 지원하는 범위만 검사할 수 있다.
   - 생태계가 늘 때 데이터팩과 갱신 책임도 늘어난다.
3. **전체 OSV DB 포함**
   - 알려진 문제의 범위가 가장 넓다.
   - 초기 배포와 지속 갱신 부담이 가장 크며 M1 범위에는 과하다.

## 이 프로젝트에 맞는 권장안

M1은 hook·판정·명령 출처·로그·캐시 계약을 먼저 검증하므로 OSV/MAL 데이터팩을 필수 범위에서 제외한다. 악성 패키지 oracle은 체크인한 작은 고정 fixture metadata로 검증한다.

후속 도입 순서는 다음이 적절하다.

1. npm 범위의 `MAL-` 중심 악성 패키지 인덱스를 별도 버전 데이터팩으로 제공한다.
2. 지원 생태계가 늘면 해당 생태계의 취약점 데이터팩을 선택적으로 추가한다.
3. 모든 생태계의 전체 DB는 기본 패키지에 넣지 않는다.

여기서 `MAL-` 인덱스는 OSV가 별도 파일로 제공하는 공식 다운로드 이름이 아니다. OSV 공식 덤프는 전체 DB와 생태계별 DB를 제공한다. 작은 악성 패키지 전용 팩을 쓰려면 OpenSSF Malicious Packages의 OSV 레코드를 고정한 commit에서 선별하고, 철회·경계 사례를 처리한 뒤 Secure Onboard가 자체 데이터팩으로 생성해야 한다.

## 후속 데이터 갱신 흐름

평판 데이터 기능을 도입하면 매 작업마다 전체 데이터를 다시 받지 않고 다음 순서로 처리한다.

1. 사용자 영역의 로컬 데이터 매니페스트와 최대 허용 나이를 확인한다.
2. 유효한 데이터가 있으면 재사용한다.
3. 없거나 오래됐을 때만 공식 OSV 덤프 또는 프로젝트가 서명한 `MAL-` 팩을 별도 갱신 작업으로 내려받는다.
4. 출처·라이선스·생성 시각을 확인한다. 공식 OSV 덤프는 같은 GCS object generation에 precondition을 걸고 응답의 CRC32C를 내려받은 바이트와 대조하며, MD5는 응답에 제공된 경우만 보조로 확인한다. 자체 `MAL-` 팩은 프로젝트 서명과 원본 commit·레코드 disposition을 검증한다.
5. 로컬 SHA-256과 원본 객체 식별정보를 매니페스트에 기록하고 데이터를 원자적으로 교체한다.
6. 데이터 version을 증거·작업 cache key에 포함한다.

대상 패키지 이름·버전을 외부 조회에 보낼지 여부는 데이터 기능 도입 시 별도 사용자 고지와 정책으로 결정한다. M1은 네트워크 평판 조회를 하지 않는다.

데이터 기능이 활성화된 뒤 필수 데이터가 없거나 손상되고 갱신도 실패하면 보호 action은 `HIGH guardrail.scan_failure`, read-only scan은 같은 rule의 HIGH finding report다. 데이터 기능이 아직 지원되지 않는 M1에서는 remote registry install의 실제 bytes를 검증할 수 없어 fail-closed HIGH로 막는다. exact local immutable artifact의 선택적 평판 정보만 없을 때는 `npm.reputation_unknown` LOW와 기능 한계를 표시한다.

GCS 체크섬은 전송 중 손상 검증에 쓰고, 로컬 SHA-256은 같은 입력을 다시 식별하기 위한 지문으로 쓴다. OSV 데이터 덤프 문서는 별도 배포 서명을 약속하지 않으므로, 이 값들만으로 공급자 진위를 증명했다고 표현하면 안 된다. Secure Onboard가 만든 `MAL-` 팩은 프로젝트 릴리스 키로 서명하고 클라이언트가 그 서명을 검증하는 방안을 구현 전에 확정해야 한다.

각 데이터팩에는 최소한 다음 정보를 기록해야 한다.

- 생성·갱신 시각과 최대 허용 나이
- 포함 생태계
- 원본 출처와 라이선스
- 원본 객체 체크섬, 로컬 SHA-256과 사용 가능한 배포 서명
- 철회·경계성·분류 미완료 레코드의 처리 방식과 disposition

OSV는 전체·생태계별 다운로드와 변경 레코드 목록을 공식 제공한다. 배포 방식은 [OSV 데이터 덤프 문서](https://google.github.io/osv.dev/data/)를 기준으로 구현한다.

최대 허용 나이를 며칠로 할지는 아직 미결이다. 구현 전에 데이터 변경 빈도, 다운로드 크기와 오프라인 사용 기간을 비교해 결정한다.
